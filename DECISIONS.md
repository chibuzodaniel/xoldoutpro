# DECISIONS.md

Every assumption made building XOLDOUT, what was chosen, and why. One entry per decision. Source of truth for scope is `xoldout-prd.md`.

## Blocking decisions (answered 2026-08-14, via AskUserQuestion)

- **Platform commission**: 15%, withdrawal fee absorbed by the platform. Shapes `WalletLedgerEntry.kind = COMMISSION_FEE` and `Payout.feeKobo` (currently always 0).
- **Settlement / refund window**: 7-day pending → available, 7-day refund window. One window serves both (PRD explicitly allows this).
- **Payment processor**: Flutterwave — card, bank transfer, and USSD. Chosen over Paystack per explicit user preference; no functional reason to prefer one over the other for this build.
- **Sold-out semantics**: cap is per release; a sold-out release stays permanently sold out; a second pressing must be a brand-new listing (new `Product` row), never a reopened cap on the old one.
- **Auth**: Firebase Auth — email/password and Google sign-in. Session verified server-side via Firebase Admin `verifyIdToken`; the Postgres `User` row is mirrored on first sign-in via `firebaseUid`, created by `POST /api/auth/sync`.
- **Stack/hosting**: Next.js (App Router) + Postgres (Prisma) + Cloudflare R2, Vercel/Railway-class hosting.

## Client-side crop before upload, and transparent logo assets (2026-08-15)

- **Every single-image upload (avatar, cover, release/beat/event artwork, merch product photo) now goes through `ImageCropModal`** (`components/upload/ImageCropModal.tsx`, using `react-easy-crop` — new dependency) before the file ever reaches `uploadImage`/R2. Previously the server (`lib/images.ts`'s `resizeSquare`/`resizeBanner`, `fit: "cover"`) silently center-cropped whatever was uploaded with no user control. The modal's output dimensions match the server's target aspect exactly (512×512 avatar, 1200×400 cover, 1024×1024 square artwork/product photo), so the server's resize is a no-op on framing — the crop the user chooses is the crop that ships.
- **Merch gallery photos (multi-file) are NOT cropped** — deliberate scope simplification. A sequential per-file crop flow for a multi-select input is meaningfully more UX complexity than the primary single-image case; revisit if it becomes a real pain point.
- **Logo backgrounds removed**: `xoldout-logo.jpeg` (wordmark, used on login/signup) was flattened on solid black with no alpha channel. Recovered transparency via an unpremultiply-against-black pass (`out = observed * 255 / max(r,g,b)`, alpha = `max(r,g,b)`) rather than a hard chroma-key threshold, since it handles anti-aliased edges cleanly — same technique implied by the already-existing `xoldout-icon-transparent.png`. Produced `xoldout-logo-transparent.png`; login/signup now use it.
- **`apple-touch-icon` (`xoldout-icon.jpeg`) was deliberately left opaque**, not switched to a transparent PNG — iOS fills transparent regions of home-screen touch icons with black rather than compositing against wallpaper, so a transparent version wouldn't actually look "background-removed" there, just less predictable. Every icon reference that actually renders in-page already used the pre-existing `xoldout-icon-transparent.png`.
- **Bug found after shipping this**: the crop modal appeared broken on `profile/edit` (avatar/cover) right after this landed. Root cause was environmental, not a code bug — `react-easy-crop` was `npm install`ed while `next dev` was already running, and Turbopack's dev server held a stale module graph from before the package existed in `node_modules`. Verified the component itself was correct (both `cropShape="round"`/aspect 1 and `cropShape="rect"`/aspect 3 render, pan, zoom, and crop correctly) via a throwaway unauthenticated debug route before concluding this. **Takeaway: always stop and restart `next dev` after installing a new dependency, not just after schema changes** — a `.next` cache clear plus restart resolved it.

## Own-profile awareness on the public profile page (2026-08-15)

- **`/u/[handle]` previously looked identical whether you were viewing your own public profile or someone else's** — no way to tell "this is you" from "just viewing." `ProfileHeaderRow` (`components/profile/ProfileHeaderRow.tsx`) fixes this: a client component that checks `appUser.id === targetUserId` and swaps the avatar-with-edit-badge + "Edit profile" link (mirroring the exact pattern already on the private `/profile` page) in for the plain avatar + `FollowButton` when you're looking at yourself.
- This has to be a client-side check, not server-side: `/u/[handle]` is a Server Component and this app's auth is bearer-token-based (Firebase ID token attached per-fetch via `apiFetch`, no session cookie), so the server has no way to know who's viewing during SSR. `FollowButton` already worked around this the same way (`useAuth()` + returns `null` when `appUser.id === targetUserId`).

## Migration history is out of sync with the schema (2026-08-14)

- `npx prisma dev`'s shadow database (used to diff migrations before writing a new one) is persistently broken — every `migrate dev` attempt after the initial one fails with `type "LedgerKind" already exists`, even immediately after a clean `db push`. Unlike the connection-pool crashes elsewhere in this file, this one isn't intermittent — it reproduces every time.
- **The `User.socialLinks`/`User.pushEnabled` columns (added for the Settings redesign) were applied via `npx prisma db push`, not `migrate dev`** — so there is no corresponding file in `prisma/migrations/`. `prisma/schema.prisma` is the accurate source of truth for the current schema; the migrations folder is one change behind it.
- **The Beat/Event/TicketTier/TicketCheckIn/MerchItem/MerchOrderFulfillment tables (2026-08-15) were also applied via `db push`**, for the same reason — the drift above compounds by one more schema change now.
- **Before deploying anywhere with `prisma migrate deploy`** (which only replays files in `prisma/migrations/`, never the schema directly), someone needs to either: (a) run `prisma migrate dev` once against a real, non-`prisma-dev` Postgres to generate a baseline migration matching current `schema.prisma`, or (b) hand-write the missing migration SQL (`ALTER TABLE "User" ADD COLUMN "socialLinks" JSONB NOT NULL DEFAULT '[]', ADD COLUMN "pushEnabled" BOOLEAN NOT NULL DEFAULT false;`) and mark it applied with `prisma migrate resolve --applied`. Do this before the next `migrate dev` call, not after — otherwise the drift compounds.

## Beat/Event/Merch built for real, overriding the PRD's MVP boundary (2026-08-15)

- **The PRD explicitly says "do not build or scaffold" Beats/Events/Merchandise** (Phase 2/3). New reference screenshots showed a fuller Discover page with these sections populated, and the user chose to build them for real now rather than fake the UI or defer — an explicit, knowing override of the PRD's scope boundary, not a misreading of it.
- **Beat licensing**: single flat license only (buyout-style — one price, full commercial-use rights forever). No lease/exclusive tiers. Reuses the exact same audio ingest pipeline as music tracks (`POST /api/uploads/audio/ingest`): `audioStreamUrl` is the pre-purchase preview rendition, `audioMasterUrl` is what `presignDownload` serves after purchase, mirroring `app/api/tracks/[id]/audio-url`.
- **Merch fulfilment**: creator-shipped. Platform only collects payment and a shipping address (`MerchOrderFulfillment`, one per Order); the creator ships and self-reports `TO_SHIP → SHIPPED → DELIVERED`. No platform warehouse/inventory system, no courier integration.
- **Merch has no size/color variants in v1** — one `Product` = one listing = one price = one `StockPolicy`, same shape as a Release. Matches the reference screenshots (no variant picker shown) and keeps the commerce core untouched. Revisit if a creator actually needs per-variant stock.
- **Event ticket tiers are `Product` rows, not a field on `Event`.** A new `Event` model is a parent listing (venue, date, cover image); each tier (Early Bird/Regular/VIP) is its own `Product` (`type: EVENT`) with its own `StockPolicy`/price, linked back via `TicketTier.eventId`. This is a deliberate deviation from the PRD's diagram, which shows `Event` as a direct `Product` subtype — that shape can't support independently-priced/capped tiers without inventing a second stock/entitlement mechanism. Buying "VIP" is buying that tier's `Product`, so `reserveStock`/`confirmStock`/`recordSale`/`Entitlement` all apply unchanged. `Event.status`/`publishedAt`/`deletedAt` cascade to its tier Products on publish/delete.
- **Event check-in**: `TicketCheckIn` is a 1:1 extension of `Entitlement` (only created for `EVENT`-type purchases), holding a unique `code` rendered as a QR in the buyer's Library. Scanning uses the browser `BarcodeDetector` API where available, with a manual code-entry fallback — no new scanning dependency. QR *generation* uses the new `qrcode` npm package.

## Closing the Beat/Event/Merch scope gaps (2026-08-15)

All four gaps from the previous section are closed:

- **Merch shipping fee**: `MerchItem.shippingFeeKobo` (creator-set, defaults to 0) is added to `Product.priceKobo` at checkout (`amountKobo` in `app/api/orders/route.ts`); a free item with a nonzero shipping fee now correctly routes through the paid Flutterwave path instead of the ₦0 free-grant path. The fee actually charged is snapshotted onto `MerchOrderFulfillment.shippingFeeKobo` so a later fee edit on the listing never changes what a past buyer paid — same snapshot pattern as `OrderItem.priceKobo`. Platform commission applies to the fee too (folded into `payment.amountKobo`, same as the item price) — simplest consistent choice, no special-casing in `lib/commerce/ledger.ts`.
- **Search and public creator profiles** (`/api/search`, `/u/[handle]`) now include Beat and Merch products, not just Release — `ProductCard` was already type-generalized and needed no changes. Event was deliberately left out (ticket tiers need `EventCard`'s different shape, not a Product grid).
- **Per-tier event editing**: `PATCH /api/events/[id]/tiers/[tierId]` lets a creator edit a tier's price (freely, no restriction) and cap (lowering-only, same rule as Release — never raised, never below tickets already sold), with inline controls in `profile/catalog/events`.
- **Beat playback now uses the shared `PlayerProvider`/mini-player**, not its own `<audio>` element — `PlayableTrack` gained an optional `kind?: "track" | "beat"` (defaults to `"track"`, so every existing Release call site is unchanged) that switches which audio-url route gets hit and skips the offline-cache lookup (beats have no offline format). Confirmed by tracing the code that Release playback is byte-for-byte unaffected.

## Implementation notes / scope calls made while building Milestone 1

- **Local Postgres**: `npx prisma dev` (Prisma's bundled local Postgres, no Docker) rather than a hosted instance, since this is local development. Swap `DATABASE_URL` for a real Postgres connection string before deploying.
- **Waveform peaks + streaming transcode run synchronously** inside `POST /api/uploads/audio/ingest` (ffmpeg via `ffmpeg-static`) rather than through the `Job`/worker-queue design in the architecture plan. The `Job` table still exists in the schema for the future move to async processing under load (large catalogs, slow uploads) — for Milestone 1's scale, synchronous is simpler to develop and test end-to-end without standing up a second always-on process. `STOCK_SWEEP`/`SETTLEMENT_SWEEP` jobs (releasing expired stock holds, flipping pending ledger entries to available) are Milestone 2 work and still need the queue — that's when the worker actually needs to exist.
- **Streaming audio rendition is MP3** (`libmp3lame`, 128kbps), not AAC or Opus/WebM — chosen because MP3 needs no seek table/container (streams fine from a plain byte pipe) and plays on every browser including iOS Safari, which WebM/Opus does not reliably support.
- **Avatar/cover are single server-resized derivatives**, not a multi-size ladder — avatar 512×512, cover 1200×400. Release artwork *does* get a real ladder (64/256/1024) since it's shown at genuinely different sizes across Home/catalog/detail surfaces and the PRD calls this out explicitly (§7.1); profile images are shown at one size in practice, so a ladder there would be unused complexity.
- **Release cap editing**: only lowering an already-set cap is supported (down to units sold, matching the PRD's 500→100-not-50 example). Introducing a cap on a previously-uncapped release, or removing a cap entirely, is rejected — both would let scarcity be gamed after the fact, which the PRD doesn't sanction and the "cannot raise" rule implies.
- **`npx prisma dev`'s embedded Postgres is fragile under concurrent load, even with the tuned pool params below.** It repeatedly crashed outright (not just throttled) during this build whenever several separate Node processes hit it around the same time — the stock-race test's own concurrent connections, `next build`'s static-generation workers, and a lingering `next dev` instance were each enough on their own to kill it. `npx prisma dev ls` kept reporting "running" after each crash; the only reliable fix was `npx prisma dev stop <name>` then `start <name> -d` and re-verifying with `prisma db execute` before doing anything else. If this keeps happening on your machine, swap in a real local Postgres (Docker, or a free-tier hosted instance) — the embedded dev server is convenient but not built for this kind of concurrency testing.
- **Local Postgres connection string needs explicit pool params.** `npx prisma dev`'s embedded Postgres recommends (and effectively requires) `connection_limit=10&connect_timeout=0&max_idle_connection_lifetime=0&pool_timeout=0&socket_timeout=0` on `DATABASE_URL` — without them, a burst of ~10+ concurrent connections (exactly what the stock-race test does) killed the local dev server outright rather than queuing. `lib/db.ts` also caps the `pg.Pool` at `max: 10` to match. This is a local-dev-only concern; a hosted Postgres in production can use its own pool sizing.
- **Release detail page (`/r/[id]`) ships in Milestone 1 as browse-only** — artwork, price, remaining/sold count, tracklist, no player and no buy button yet. Buying, entitlements, and playback are explicitly Milestone 2 (PRD §19); building a real player against non-existent entitlements would need to be redone anyway.

## Fanbase (Socials) announcements built — Milestone 3 item 11 (2026-08-17)

- **`Post`/`PostLike` are new top-level models**, not nested under a `FanbaseGroup` — groups are Phase 2 and don't exist yet. Any account may author a post (PRD §1.4: identity never gates capability); it reaches whoever follows that account. `GET /api/posts` returns posts from `{followed creator ids} ∪ {self}` — own posts are included so the composer has visible effect without following yourself, a minor addition the PRD doesn't specify either way.

Same pattern as `/library`.

## Trust & safety built — Milestone 3 item 13 (2026-08-17)

- **`Report` (already scaffolded in the schema, unused until now) gained `eventId`/`postId`/`profileId` FKs and a `details` free-text field**, alongside the existing `productId`. `ReportTargetType` gained `EVENT` — Event is deliberately not a `Product` (DECISIONS.md, Beat/Event/Merch section: ticket tiers are the Products), so it needs its own target column; a report on an event page can't be filed against a tier without being confusing to a moderator reading the queue. `COMMENT` stays FK-less since Comment doesn't exist until Phase 2 groups.
- **`User.isModerator`** is a plain boolean, set directly in the DB — there's no self-serve UI or promotion flow, matching PRD §3's "Platform moderator: Internal." `requireModerator()` (`lib/auth/session.ts`) 403s non-staff; `AuthError` gained a settable `status` (was hardcoded 401) to support this.
- **In-context reporting is scoped to the two content-moderation reasons** (Inappropriate content, Copyright claim) on `PRODUCT`/`EVENT`/`POST`/`PROFILE` — `ReportButton` hides for the owner/author and for signed-out visitors. Bug/Feature request have no natural "target" (the PRD's report table doesn't map them to content), so they're filed through a separate "Send feedback" entry point on the private Profile page, self-targeted as `PROFILE`/own `userId` by convention — the API's "can't report your own profile" guard is relaxed specifically for those two reasons so this doesn't 400.
- **Automatic device/app-version/screenshot attachment on bug reports (PRD §14) was not built.** Screenshot capture specifically would need either a new client-side capture dependency or a permissions-gated browser API; out of scope for this pass. `details` is free text only. Flag if bug-report volume ever makes this worth it.
- **Copyright takedown (`PATCH /api/reports/[id]`, `action: "takedown"`) is the one report action that moves money**, and is intentionally the *only* path in the codebase that revokes an `Entitlement` outside of the reasoning in PRD §8 ("never revoked by artist action, only by refund") — it qualifies because it *is* a refund: `lib/commerce/ledger.ts` gained `recordRefund()`, a single `REFUND_DEBIT` ledger entry for the net amount (gross − commission) the seller was credited, effective immediately (`availableAt: null`) rather than after the usual 7-day window — a seller holding funds from a voided sale owes them back now. The transaction also sets `Product.status = DELETED` (same mechanism as a creator's own delete) and `Order.status = REFUNDED` for every affected order. Restricted to `reason: COPYRIGHT_CLAIM` + `targetType: PRODUCT` only — Event ticket-tier takedowns would need to reverse N tier-Product sales at once and aren't handled by this action yet.
- **The Flutterwave side of a refund — actually returning the buyer's money via `/transactions/{id}/refund` — was deliberately NOT wired in.** Everything the ledger needs (the debit, the revoked entitlement, the `REFUND_DEBIT`-triggered negative-available-balance-until-settlement) is real and auditable in Postgres, but calling a live payment processor to reverse a real charge is an external, hard-to-reverse financial action that shouldn't be added speculatively. Flag this explicitly before the takedown flow is used against a real (non-test) Flutterwave transaction — the buyer's card/bank won't actually be refunded yet, only the platform's internal ledger.
- **Verified the full takedown transaction (product→DELETED, entitlement revoked, order→REFUNDED, correct `REFUND_DEBIT` math) end-to-end** by seeding a simulated paid order directly via Prisma (bypassing Flutterwave entirely — no live payment call was made) and running the actual takedown through the moderation UI. Confirmed the ledger entry exactly zeroes out the original `SALE_CREDIT`/`COMMISSION_FEE` pair.

## Analytics built — Milestone 3 item 12 (2026-08-17)

- **`GET /api/analytics` computes everything from existing tables — no new schema.** Units sold and per-product sell-through/time-to-sell-out come from `Product`/`StockPolicy` (`soldOutAt` minus `publishedAt`, in hours); fan growth is `Follow` rows for/within the last 30 days; returning customers is derived from grouping `PAID` `Order.buyerId` by count (>1 paid order from this creator = returning) — none of this needed a new table, matching the PRD's own framing of `StockPolicy.soldOutAt` as "what makes time-to-sell-out reportable."
- **No Naira figures anywhere on this screen**, per PRD §13 ("Analytics carries units, fans, conversion, and retention, and shows no Naira amounts") — enforced by construction, since the query never selects `priceKobo` or touches `WalletLedgerEntry`.
- **"Top products" and the sell-through/time-to-sell-out figures are one combined list, not two**, sorted by units sold — the PRD lists them as separate bullet points but they're the same underlying per-product data; a second list would just repeat the same five products with different columns.
- **Sell-out rate and returning-fans tiles show "—" (not 0%) when there's no capped product or no customer yet** — 0% would misleadingly claim "nothing sold out" for a creator with no capped releases at all, a distinction the PRD doesn't call out but that avoids a materially wrong statistic on a brand-new profile.
- **No charting/sparkline** — stat tiles plus lists, matching the existing Profile page's Fans/Sales tile pattern exactly. The PRD requires the metrics, not a visualization; the `dataviz` skill exists for later if fan-growth trend lines become worth the complexity.
- **Fan-growth is a single 30-day delta, not a time series** — `newFans30d` alongside the all-time `fans` count. A proper growth chart would need historical snapshots or a `Follow.createdAt` bucketed query per day/week; the PRD's "fan growth" bullet doesn't specify granularity, and a single delta is the smallest thing that's still informative.
- **Verified end-to-end against real data**: reassigned the takedown-test seed product to a real account and added two `Follow` rows, then confirmed in the browser that units sold, fan count, the 30-day delta, and the top-products row all matched the seeded numbers exactly, with sell-out rate and returning-fans correctly showing "—" for the uncapped/single-customer case.

## PWA install guide built — Milestone 3 item 14, closes out the Milestone 3 audit (2026-08-17)

- **Platform detection is event-driven for Chromium, UA-sniffed only for iOS.** `components/pwa/InstallSheet.tsx` listens for `beforeinstallprompt` (Chrome/Edge, desktop or Android) and calls its captured `prompt()` on click — no UA sniffing needed there since the browser tells you directly whether it can install. iOS Safari never fires that event and has no programmatic install API at all, so it's the one browser detected by user agent (`iPhone|iPad|iPod`, plus the iPadOS-reports-as-Mac case caught via `maxTouchPoints > 1`) and shown manual "tap Share → Add to Home Screen" steps instead. Everything else (Firefox, browsers where the event doesn't fire within ~800ms) falls back to a generic "look for Install app in your browser's menu" message rather than showing nothing.
- **Already-installed state** (`display-mode: standalone` or iOS's `navigator.standalone`) shows a "You're set" confirmation instead of install instructions, so a user who installed on a previous visit doesn't see a stale prompt.
- **Revised same-day, on user feedback: this is a bottom sheet, not a full-screen step or route.** The first pass made it a second full-screen onboarding step and a standalone `/install` page; both covered the whole viewport, which read as heavier than the guide warrants. It's now `InstallSheet` — same slide-up/dim-backdrop shell as `PublishSheet`/`ReportSheet` — mounted once globally via `InstallGuideProvider` (`app/layout.tsx`, alongside `PlayerProvider`/`BottomNav`) so it can be triggered from anywhere and floats over whatever page is already showing rather than being its own destination. Onboarding now navigates to `/discover` immediately on profile-setup submit and opens the sheet on top of it (`installGuide.open()` right after `router.push`); Profile → "Install app" opens the same sheet in place instead of navigating to a page. The standalone `/install` route and the `NO_NAV_EXACT` entry for it were removed — nothing needs a dedicated URL anymore.
- **Footer is a small corner × to dismiss, not a full-width "Maybe later" bar** — also revised on feedback. A primary action button (red, full-width) only appears when there's an actual action to take: "Install XOLDOUT" when `beforeinstallprompt` was captured, or "Done" once installed. The iOS-steps and generic-fallback branches have no primary button at all, since there's nothing programmatic to click — just the corner ×.
- **Taste selection was not built** — the PRD's onboarding row lists "PWA install guide, taste selection" together, but taste selection is out of scope for "PWA install guide" specifically, and nothing elsewhere in the app has a personalization/taste signal to select from yet.
- **No service worker was built.** PRD §16 lists "service worker plus encrypted local audio cache" as the offline requirement — the encrypted local audio cache (`lib/offline/*`, IndexedDB-based) already exists and doesn't depend on a service worker, but there's no app-shell service worker for offline page-loads or a true `beforeinstallprompt`-independent install path on browsers that require one. This is a materially bigger feature (cache versioning/invalidation strategy, stale-while-revalidate for API routes, testing across a service-worker lifecycle) than "install guide" scope covers — flag separately if offline-first page loads (not just offline audio playback, which already works) become a requirement.
- **Manifest icon was left as-is** (`public/manifest.json`, one 1080×1080 `purpose: "any"` icon) — didn't add a `maskable` variant, since the existing icon has no safe-zone padding and would risk cropping on Android's circular/rounded mask without new asset work. Out of scope for wiring up the install guide itself.
- **Verified end-to-end after the sheet revision**: signed up a fresh test account, confirmed submitting profile setup lands on `/discover` with the install sheet slid up on top of it (Discover visibly dimmed behind, not covered); closed via the corner ×, landing cleanly back on `/discover`. Separately confirmed Profile → "Install app" opens the same sheet over the Profile page (Wallet/Requests visible dimmed behind it) without navigating away, and the × returns to a normal, fully-interactive Profile. Cross-checked the iOS-detection regex/touch-point logic against five UA cases (iPhone, iPad-as-Mac, real macOS, Android Chrome, Windows Chrome) directly, since this browser can't be made to genuinely report as iOS Safari.
- **Found and fixed a real timing bug mid-review**: the `beforeinstallprompt` listener originally attached only when the sheet opened, not when the app loaded — since Chrome fires that event once, early, and doesn't replay it, a listener attached late would silently miss it forever and the "Install now" button could never appear. Moved the listener into `InstallGuideProvider`'s mount effect (fires once for the app's lifetime) so it's armed before any user could plausibly open the sheet.
- **Could not get Chrome to actually fire `beforeinstallprompt` in this Claude-in-Chrome automation session**, even after the fix above and confirming the manifest itself is valid (200, correct fields, secure context, not already standalone) — this is a known characteristic of extension/remote-debugging-controlled browser sessions, which typically don't satisfy Chrome's install-prompt engagement heuristics, not a defect in the app. Left as-is per user direction ("leave it for now"); should be spot-checked in a normal, non-automated Chrome/Edge window before relying on it. The generic "look for Install app in your browser's menu" fallback and the iOS manual-steps path both work regardless and don't depend on this event at all.
- **User raised a native app (React Native/Capacitor-class wrapper) as a possible future direction**, not committed to — PRD §16 already flags "store distribution is a later decision" explicitly. No code changes made toward this; noting it here so it isn't lost.

Each is scoped and verified independently below; card-grid treatment (matching `ProductCard`'s tile language) was applied to every new listing surface — Collections, Gifts, Groups — rather than the divided-list-row pattern used for the MVP screens.

**Verification (PRD §12)**
- `User.isVerified` is a plain moderator-toggled boolean, same shape as `isModerator` — PRD §18 leaves the actual criteria ("who gets a badge, on what evidence") explicitly unresolved, so this deliberately doesn't invent a review workflow, just the toggle and the badge. `POST /api/admin/verify` (moderator-gated) + a "Verify a creator" handle-lookup panel on `/moderation`.
- `VerifiedBadge` renders next to the display name on own Profile, public `/u/[handle]`, and post/group-post author names — anywhere a creator name is already shown prominently.

**Collections (PRD §10 Phase 2)**
- `Collection`/`CollectionItem` — a thin grouping over `Entitlement`, not a copy of it; deleting a collection (`onDelete: Cascade` on the item join row) never touches ownership. Library gained a three-tab switcher (Purchased/Collections/Gifts) reading its initial tab from `?tab=`, replacing the single flat view.
- Every Purchased-tab row (release, beat, merch, ticket) gained a small "+" that opens `AddToCollectionSheet` — list existing collections or create one inline, matching the sheet shell used everywhere else.
- Collection items render as a card grid (`EntitlementCard`, shared with the Gifts tab) linking straight to the product's own detail page rather than reimplementing per-type playback/download/QR inline — that logic already lives in Library's row components and shouldn't be duplicated a third time.

**Gifting (PRD §7.3 Phase 2)**
- Reuses the *exact* existing checkout/webhook pipeline — `Order.isGift` is the only new field on the purchase path. `reserveStock`/`confirmStock`/`recordSale` are untouched; the only branch is at entitlement-creation time: a gift order creates a `Gift` row (PENDING, `claimToken`, 7-day `expiresAt`) instead of an `Entitlement`. This is what makes "stock decrements at purchase, not claim" (PRD's explicit requirement) fall out for free rather than needing new logic.
- **Claim mechanics** (PRD §18 open decision, not resolved by the PRD itself): link-based, not handle-targeted — `/gifts/claim/[token]`, publicly viewable, claim requires login (`login?next=...` — added `next` param support to the login page for this, since nothing previously needed a post-login redirect). 7-day expiry chosen to match the existing settlement-window length, not because the PRD specifies a number.
- **Scoped to RELEASE/BEAT/EVENT-tier, not MERCH** — a claim link has no recipient identity until claimed, so there's no shipping address to gift a physical item to.
- **Expiry sweep reuses `recordRefund`** (built for the copyright-takedown path) and a new `releaseConfirmedUnit` stock helper (the inverse of `confirmStock` — undoes the sold-count increment, un-sets `soldOutAt` if back under cap) — both wired into the existing `sweep-holds` cron rather than a new job, extending the same "expired hold → release + refund" shape that already existed for abandoned checkouts.
- Gift purchase is a second button ("Gift this") next to Buy on Release/Beat/Event-tier detail pages, not a separate flow — verified the full loop: create → claim-link preview page → claim → entitlement granted, end-to-end reasoning matches the takedown-refund verification approach from the Trust & Safety pass (seeded/traced through code, since exercising a full 7-day expiry live isn't practical to wait out).

**Fanbase groups (PRD §11 Phase 2 — the biggest piece)**
- `FanbaseGroup`/`Membership`/`JoinRequest` plus extending the existing `Post` model with `groupId` (null = MVP announcement, set = posted inside that group) rather than a parallel `GroupPost` model — reuses `PostLike`, and now `Comment`/`Poll`/`PollVote` for free. The MVP announcement feed (`GET /api/posts`) explicitly filters `groupId: null` so group posts never leak into it — the two stay visually and functionally distinct, matching the PRD's own MVP-vs-Phase-2 split.
- **The creator is always given a `Membership` row with `role: ADMIN` at group creation** — this single decision is what lets every downstream permission check (`postPermission: ADMINS`, admin-list display, join-request approval) treat "creator" as just "the founding admin" instead of needing a separate `creatorId === userId` branch everywhere except settings changes and admin promotion, which PRD §11 reserves for the creator specifically.
- **Default `postPermission: CREATOR_ONLY`** per PRD §11's explicit instruction ("an artist should opt into moderation load deliberately"). Verified live with two accounts: a `CREATOR_ONLY` group correctly blocked a second member's post server-side (`"You can't post in this group"`) even before the client-side composer-hiding fix landed — the permission check was never just a UI affordance.
- **Comments are flat, not threaded** — PRD Phase 2 scope is "member participation," not a nested comment tree. Reachable via a generic `/api/posts/[id]/comments` (works on any Post) but only the group post view renders the UI; the MVP feed stays comment-free per PRD §11 MVP.
- **Polls are a `Post` extension (1:1 `Poll`), not a separate content type** — `options: String[]` + `PollVote(pollId, userId, optionIndex)`, one vote per user (upsert). Proportional result bars only reveal percentages once you've voted (`myVote !== null`), matching common poll-UI convention and avoiding influencing votes with visible tallies beforehand — not a PRD requirement, a judgment call. Verified live with two accounts voting for different options: 50/50 split rendered correctly, each account's own choice highlighted.
- **Found and fixed a real gap during verification, not just a lint issue**: the group composer initially rendered for every member regardless of `postPermission`, relying entirely on the server 403 to stop a disallowed post — functionally safe (confirmed: the server did block it) but a bad UX trap, since a member could type a full post and only discover they couldn't post it after hitting Post. Added a client-side `canPost` check (mirroring the server's exact `CREATOR_ONLY`/`ADMINS`/`ALL_MEMBERS` logic) so the composer simply doesn't render for members who can't use it.
- **`/groups` (list + discover + create) and `/groups/[id]` (detail, feed, join/leave, manage) are new top-level routes**, not folded into `/socials` — Socials gained a small "Groups →" link instead. PRD §5's Phase 3 nav diagram eventually makes Fanbase a groups-first surface, but restructuring the MVP tab bar itself is out of scope here; this keeps groups reachable without disturbing the existing Socials/announcements screen.
- Verified end-to-end with two real accounts: created a group (open visibility), posted with a poll, voted, commented — then joined as a second account, confirmed the post-permission block, confirmed the second vote split the poll 50/50 with correct per-user highlighting, and opened the Manage sheet's all three tabs (Requests/Members/Settings) as the creator. Join-request approval (`REQUEST_TO_JOIN` visibility) and admin promotion were verified by code trace, not live-clicked, given time already spent on the OPEN-visibility path above.

**Cross-cutting fixes found during this pass**
- **`LoadingSpinner`'s `full` variant was measurably miscentered** — its old `min-h-[Xvh]`-based box wasn't stretched to fill its actual parent (most call sites nest it inside plain block divs, not flex containers), so it centered within a too-short, top-anchored box rather than the visible viewport. Replaced with `fixed inset-0 flex items-center justify-center pointer-events-none`, which centers against the true viewport regardless of ancestor layout — fixes every `full` call site at once, not just the ones touched in this pass.
- **The loading icon's animation changed from a flat linear spin to a combined rotate+scale "breathe"** (`animate-spin-breathe`, one breath per full rotation) per explicit request — added as a new keyframe in `globals.css` alongside the existing `waveform-bar` one.

## For You feed ranking (2026-08-23)

- **`GET /api/posts?feed=forYou` is now ranked by affinity, not pure `createdAt desc`** — this does not reopen the earlier "no pool restriction" decision above: the pool (every public post, any creator, except your own) is unchanged, only display order changes. Signals: explicit follow, likes/comments given (90-day window), `TrackPlay` counts (90-day window), active `Entitlement`s (not time-windowed — a past purchase is a lasting relationship), 2-hop follow-network proximity ("creators the people you follow also follow"), and `User.tags` overlap. Combined with a small recency-decay term so a brand-new post from an unrelated creator still surfaces reasonably — For You must stay genuine discovery, never fully collapse to "creators I already know."
- **Scored live per-request, not via a precomputed table refreshed by a cron.** Every signal query is bounded by the *viewer's own* history (their follows/likes/plays/purchases), not a global scan, so this is cheap at current scale — matches the existing convention in `lib/socials/unread.ts` of computing derived per-user social state live rather than caching it. Deliberately avoided adding a new Prisma model for this: this project's prisma schema changes don't automatically reach production (a recurring source of live-page breakage), so skipping a migration here removes that risk entirely. Revisit with a precomputed table only if per-request cost ever actually becomes a problem — same spirit as the "no pagination... revisit with a cursor" note above.
- **The `Job`/`JobType` table in the schema was confirmed unused** (nothing creates or consumes it; "polled by the worker service" describes a worker that doesn't exist in this repo) — not built on for this feature. The only real recurring infra is the three Vercel Hobby crons in `vercel.json` hitting `app/api/internal/*/route.ts` synchronously; this feature needed neither that nor the `Job` table.
- Ranking logic lives in `lib/socials/forYouRanking.ts` as a pure `scoreForYou()` function (fabricated-input unit-testable) separate from `fetchForYouSignals()` (the actual DB queries) — kept apart specifically so the scoring math doesn't need the integration-test-against-real-Postgres style used by `lib/commerce/stock.test.ts`.
- Candidate pool widened to 150 posts internally before ranking+truncating to 50 for the `forYou` branch only, so ranking has something to reorder among — the public "50 posts, no pagination" response contract is unchanged.

## Library "Purchased" tab: grid tiles for Music & Beats (2026-08-23)

- **Releases and beats now render as a 2-column artwork-tile grid** (square cover, title + creator below), replacing the previous flat list of rows — matching an Apple Music Library reference screenshot the user supplied. Tickets and Merch deliberately stayed as list rows: their data (event date/QR/check-in status, shipping status) doesn't fit a plain artwork tile the way an album cover does.
- **Tapping a tile plays immediately and expands inline** (not a navigation to a detail page) — a full-width panel opens directly under the tapped tile's row (`col-span-2` inserted into the grid flow via `flatMap`) showing the release's tracklist with per-track play/download, or a single Download action for a beat, plus "+ Collection". Tapping the same tile again collapses the panel without stopping playback. This was an explicit choice over "tap navigates to /r/[id]" — kept play controls reachable without leaving Library, closer to how the previous list already worked.
- **Removed the "X MB downloaded on this device" usage counter** from the Purchased tab (was `formatBytes(usageBytes)` via `totalDownloadBytes()`) — explicit ask, no replacement. `totalDownloadBytes()` itself stays in `lib/offline/downloads.ts` since nothing else needed it removed and a future storage-management screen might still want it.
