# DECISIONS.md

Every assumption made building XOLDOUT, what was chosen, and why. One entry per decision. Source of truth for scope is `xoldout-prd.md`.

## Blocking decisions (answered 2026-08-14, via AskUserQuestion)

- **Platform commission**: 15%, withdrawal fee absorbed by the platform. Shapes `WalletLedgerEntry.kind = COMMISSION_FEE` and `Payout.feeKobo` (currently always 0).
- **Settlement / refund window**: 7-day pending → available, 7-day refund window. One window serves both (PRD explicitly allows this).
- **Payment processor**: Flutterwave — card, bank transfer, and USSD. Chosen over Paystack per explicit user preference; no functional reason to prefer one over the other for this build.
- **Sold-out semantics**: cap is per release; a sold-out release stays permanently sold out; a second pressing must be a brand-new listing (new `Product` row), never a reopened cap on the old one.
- **Auth**: Firebase Auth — email/password and Google sign-in. Session verified server-side via Firebase Admin `verifyIdToken`; the Postgres `User` row is mirrored on first sign-in via `firebaseUid`, created by `POST /api/auth/sync`.
- **Stack/hosting**: Next.js (App Router) + Postgres (Prisma) + Cloudflare R2, Vercel/Railway-class hosting.

## Client-side crop before upload, and transparent logo assets (2026-08-15)

- **Every single-image upload (avatar, cover, release/beat/event artwork, merch product photo) now goes through `ImageCropModal`** (`components/upload/ImageCropModal.tsx`, using `react-easy-crop` — new dependency) before the file ever reaches `uploadImage`/R2. Previously the server (`lib/images.ts`'s `resizeSquare`/`resizeBanner`, `fit: "cover"`) silently center-cropped whatever was uploaded with no user control. The modal's output dimensions match the server's target aspect exactly (512×512 avatar, 1200×400 cover, 1024×1024 square artwork/product photo), so the server's resize is a no-op on framing — the crop the user chooses is the crop that ships.
- **Merch gallery photos (multi-file) are NOT cropped** — deliberate scope simplification. A sequential per-file crop flow for a multi-select input is meaningfully more UX complexity than the primary single-image case; revisit if it becomes a real pain point.
- **Logo backgrounds removed**: `xoldout-logo.jpeg` (wordmark, used on login/signup) was flattened on solid black with no alpha channel. Recovered transparency via an unpremultiply-against-black pass (`out = observed * 255 / max(r,g,b)`, alpha = `max(r,g,b)`) rather than a hard chroma-key threshold, since it handles anti-aliased edges cleanly — same technique implied by the already-existing `xoldout-icon-transparent.png`. Produced `xoldout-logo-transparent.png`; login/signup now use it.
- **`apple-touch-icon` (`xoldout-icon.jpeg`) was deliberately left opaque**, not switched to a transparent PNG — iOS fills transparent regions of home-screen touch icons with black rather than compositing against wallpaper, so a transparent version wouldn't actually look "background-removed" there, just less predictable. Every icon reference that actually renders in-page already used the pre-existing `xoldout-icon-transparent.png`.
- **Bug found after shipping this**: the crop modal appeared broken on `profile/edit` (avatar/cover) right after this landed. Root cause was environmental, not a code bug — `react-easy-crop` was `npm install`ed while `next dev` was already running, and Turbopack's dev server held a stale module graph from before the package existed in `node_modules`. Verified the component itself was correct (both `cropShape="round"`/aspect 1 and `cropShape="rect"`/aspect 3 render, pan, zoom, and crop correctly) via a throwaway unauthenticated debug route before concluding this. **Takeaway: always stop and restart `next dev` after installing a new dependency, not just after schema changes** — a `.next` cache clear plus restart resolved it.

## Own-profile awareness on the public profile page (2026-08-15)

- **`/u/[handle]` previously looked identical whether you were viewing your own public profile or someone else's** — no way to tell "this is you" from "just viewing." `ProfileHeaderRow` (`components/profile/ProfileHeaderRow.tsx`) fixes this: a client component that checks `appUser.id === targetUserId` and swaps the avatar-with-edit-badge + "Edit profile" link (mirroring the exact pattern already on the private `/profile` page) in for the plain avatar + `FollowButton` when you're looking at yourself.
- This has to be a client-side check, not server-side: `/u/[handle]` is a Server Component and this app's auth is bearer-token-based (Firebase ID token attached per-fetch via `apiFetch`, no session cookie), so the server has no way to know who's viewing during SSR. `FollowButton` already worked around this the same way (`useAuth()` + returns `null` when `appUser.id === targetUserId`).

## Migration history is out of sync with the schema (2026-08-14)

- `npx prisma dev`'s shadow database (used to diff migrations before writing a new one) is persistently broken — every `migrate dev` attempt after the initial one fails with `type "LedgerKind" already exists`, even immediately after a clean `db push`. Unlike the connection-pool crashes elsewhere in this file, this one isn't intermittent — it reproduces every time.
- **The `User.socialLinks`/`User.pushEnabled` columns (added for the Settings redesign) were applied via `npx prisma db push`, not `migrate dev`** — so there is no corresponding file in `prisma/migrations/`. `prisma/schema.prisma` is the accurate source of truth for the current schema; the migrations folder is one change behind it.
- **The Beat/Event/TicketTier/TicketCheckIn/MerchItem/MerchOrderFulfillment tables (2026-08-15) were also applied via `db push`**, for the same reason — the drift above compounds by one more schema change now.
- **Before deploying anywhere with `prisma migrate deploy`** (which only replays files in `prisma/migrations/`, never the schema directly), someone needs to either: (a) run `prisma migrate dev` once against a real, non-`prisma-dev` Postgres to generate a baseline migration matching current `schema.prisma`, or (b) hand-write the missing migration SQL (`ALTER TABLE "User" ADD COLUMN "socialLinks" JSONB NOT NULL DEFAULT '[]', ADD COLUMN "pushEnabled" BOOLEAN NOT NULL DEFAULT false;`) and mark it applied with `prisma migrate resolve --applied`. Do this before the next `migrate dev` call, not after — otherwise the drift compounds.

## Mid-build change (2026-08-14)

- **Firebase scope narrowed to Auth + push (FCM) only.** Originally proposed Auth.js with Credentials+Google; user redirected mid-build to Firebase Auth specifically, plus Firebase Cloud Messaging for push notifications. Postgres/Prisma remained the system of record for everything else (money, stock, entitlements) — nothing in the approved architecture/schema plan changed except the auth provider. `User.fcmTokens` added to receive push later; no push-sending code exists yet (nothing in Milestone 1/2 requires it — revisit when Fanbase announcements or purchase confirmations are built).

## Should-know defaults (PRD §20 — no objection raised, proceeding with recommended default)

- Money stored as integer **kobo**, never floats (`priceKobo`, `amountKobo`, etc. throughout).
- Free releases **may** carry a quantity cap (`priceKobo = 0` and `StockPolicy.cap` are independent).
- Default preview length when a track is ≥30s: **30s**. Shorter tracks default to a custom length capped at their own duration.
- Pricing is **per release only** in MVP — no per-track pricing within an EP/album.
- Upload limits: audio ≤ **200MB** per file, ≤ **30 tracks** per release.
- Repo root is `xoldOutpro/` (this directory); PRD files stay here, app code lives in `web/`.
- No Figma/brand file was provided — UI built from the design tokens and screen reference in `xoldout-prd.html` (dark theme, serif display type, `#E11D2E` accent).
- No staging environment yet — local (`prisma dev`) + production only.

## Beat/Event/Merch built for real, overriding the PRD's MVP boundary (2026-08-15)

- **The PRD explicitly says "do not build or scaffold" Beats/Events/Merchandise** (Phase 2/3). New reference screenshots showed a fuller Discover page with these sections populated, and the user chose to build them for real now rather than fake the UI or defer — an explicit, knowing override of the PRD's scope boundary, not a misreading of it.
- **Beat licensing**: single flat license only (buyout-style — one price, full commercial-use rights forever). No lease/exclusive tiers. Reuses the exact same audio ingest pipeline as music tracks (`POST /api/uploads/audio/ingest`): `audioStreamUrl` is the pre-purchase preview rendition, `audioMasterUrl` is what `presignDownload` serves after purchase, mirroring `app/api/tracks/[id]/audio-url`.
- **Merch fulfilment**: creator-shipped. Platform only collects payment and a shipping address (`MerchOrderFulfillment`, one per Order); the creator ships and self-reports `TO_SHIP → SHIPPED → DELIVERED`. No platform warehouse/inventory system, no courier integration.
- **Merch has no size/color variants in v1** — one `Product` = one listing = one price = one `StockPolicy`, same shape as a Release. Matches the reference screenshots (no variant picker shown) and keeps the commerce core untouched. Revisit if a creator actually needs per-variant stock.
- **Event ticket tiers are `Product` rows, not a field on `Event`.** A new `Event` model is a parent listing (venue, date, cover image); each tier (Early Bird/Regular/VIP) is its own `Product` (`type: EVENT`) with its own `StockPolicy`/price, linked back via `TicketTier.eventId`. This is a deliberate deviation from the PRD's diagram, which shows `Event` as a direct `Product` subtype — that shape can't support independently-priced/capped tiers without inventing a second stock/entitlement mechanism. Buying "VIP" is buying that tier's `Product`, so `reserveStock`/`confirmStock`/`recordSale`/`Entitlement` all apply unchanged. `Event.status`/`publishedAt`/`deletedAt` cascade to its tier Products on publish/delete.
- **Event check-in**: `TicketCheckIn` is a 1:1 extension of `Entitlement` (only created for `EVENT`-type purchases), holding a unique `code` rendered as a QR in the buyer's Library. Scanning uses the browser `BarcodeDetector` API where available, with a manual code-entry fallback — no new scanning dependency. QR *generation* uses the new `qrcode` npm package.
- Full architecture/schema plan (including the reasoning above) is preserved at `C:\Users\user\.claude\plans\reflective-fluttering-volcano.md`.

## Closing the Beat/Event/Merch scope gaps (2026-08-15)

All four gaps from the previous section are closed:

- **Merch shipping fee**: `MerchItem.shippingFeeKobo` (creator-set, defaults to 0) is added to `Product.priceKobo` at checkout (`amountKobo` in `app/api/orders/route.ts`); a free item with a nonzero shipping fee now correctly routes through the paid Flutterwave path instead of the ₦0 free-grant path. The fee actually charged is snapshotted onto `MerchOrderFulfillment.shippingFeeKobo` so a later fee edit on the listing never changes what a past buyer paid — same snapshot pattern as `OrderItem.priceKobo`. Platform commission applies to the fee too (folded into `payment.amountKobo`, same as the item price) — simplest consistent choice, no special-casing in `lib/commerce/ledger.ts`.
- **Search and public creator profiles** (`/api/search`, `/u/[handle]`) now include Beat and Merch products, not just Release — `ProductCard` was already type-generalized and needed no changes. Event was deliberately left out (ticket tiers need `EventCard`'s different shape, not a Product grid).
- **Per-tier event editing**: `PATCH /api/events/[id]/tiers/[tierId]` lets a creator edit a tier's price (freely, no restriction) and cap (lowering-only, same rule as Release — never raised, never below tickets already sold), with inline controls in `profile/catalog/events`.
- **Beat playback now uses the shared `PlayerProvider`/mini-player**, not its own `<audio>` element — `PlayableTrack` gained an optional `kind?: "track" | "beat"` (defaults to `"track"`, so every existing Release call site is unchanged) that switches which audio-url route gets hit and skips the offline-cache lookup (beats have no offline format). Confirmed by tracing the code that Release playback is byte-for-byte unaffected.

## Implementation notes / scope calls made while building Milestone 1

- **Local Postgres**: `npx prisma dev` (Prisma's bundled local Postgres, no Docker) rather than a hosted instance, since this is local development. Swap `DATABASE_URL` for a real Postgres connection string before deploying.
- **Waveform peaks + streaming transcode run synchronously** inside `POST /api/uploads/audio/ingest` (ffmpeg via `ffmpeg-static`) rather than through the `Job`/worker-queue design in the architecture plan. The `Job` table still exists in the schema for the future move to async processing under load (large catalogs, slow uploads) — for Milestone 1's scale, synchronous is simpler to develop and test end-to-end without standing up a second always-on process. `STOCK_SWEEP`/`SETTLEMENT_SWEEP` jobs (releasing expired stock holds, flipping pending ledger entries to available) are Milestone 2 work and still need the queue — that's when the worker actually needs to exist.
- **Streaming audio rendition is MP3** (`libmp3lame`, 128kbps), not AAC or Opus/WebM — chosen because MP3 needs no seek table/container (streams fine from a plain byte pipe) and plays on every browser including iOS Safari, which WebM/Opus does not reliably support.
- **Avatar/cover are single server-resized derivatives**, not a multi-size ladder — avatar 512×512, cover 1200×400. Release artwork *does* get a real ladder (64/256/1024) since it's shown at genuinely different sizes across Home/catalog/detail surfaces and the PRD calls this out explicitly (§7.1); profile images are shown at one size in practice, so a ladder there would be unused complexity.
- **Release cap editing**: only lowering an already-set cap is supported (down to units sold, matching the PRD's 500→100-not-50 example). Introducing a cap on a previously-uncapped release, or removing a cap entirely, is rejected — both would let scarcity be gamed after the fact, which the PRD doesn't sanction and the "cannot raise" rule implies.
- **`npx prisma dev`'s embedded Postgres is fragile under concurrent load, even with the tuned pool params below.** It repeatedly crashed outright (not just throttled) during this build whenever several separate Node processes hit it around the same time — the stock-race test's own concurrent connections, `next build`'s static-generation workers, and a lingering `next dev` instance were each enough on their own to kill it. `npx prisma dev ls` kept reporting "running" after each crash; the only reliable fix was `npx prisma dev stop <name>` then `start <name> -d` and re-verifying with `prisma db execute` before doing anything else. If this keeps happening on your machine, swap in a real local Postgres (Docker, or a free-tier hosted instance) — the embedded dev server is convenient but not built for this kind of concurrency testing.
- **Local Postgres connection string needs explicit pool params.** `npx prisma dev`'s embedded Postgres recommends (and effectively requires) `connection_limit=10&connect_timeout=0&max_idle_connection_lifetime=0&pool_timeout=0&socket_timeout=0` on `DATABASE_URL` — without them, a burst of ~10+ concurrent connections (exactly what the stock-race test does) killed the local dev server outright rather than queuing. `lib/db.ts` also caps the `pg.Pool` at `max: 10` to match. This is a local-dev-only concern; a hosted Postgres in production can use its own pool sizing.
- **Release detail page (`/r/[id]`) ships in Milestone 1 as browse-only** — artwork, price, remaining/sold count, tracklist, no player and no buy button yet. Buying, entitlements, and playback are explicitly Milestone 2 (PRD §19); building a real player against non-existent entitlements would need to be redone anyway.
